# 1. Project Overview

The Customer Loyalty and Rewards Management System supports a single retail store's loyalty membership, purchase points, reward catalog and redemptions. Customers can register, log in and view their own account information. Store employees record point earnings and process redemptions. Managers maintain the reward catalog, employee access and membership status. Email notifications connect account and reward events to customer or manager messages.

The operational problem follows Activity 3: manual loyalty tracking makes it difficult to maintain accurate point balances and redemption records. This is the student's proposed system scenario; no store interview or measured business outcome is claimed in this report.

## 1.1 Objectives

Implement the architecture and entities carried forward from Activities 3-6. Provide secure customer and employee login. Maintain one loyalty account per customer. Record all balance changes through Earn, Redeem or Adjust ledger entries. Process reward stock and point deductions atomically. Expose at least 20 REST endpoints and provide working customer/reward CRUD. Integrate a logged email queue and SMTP dispatch. Test and explain the backend using Postman and MySQL.

## 1.2 Scope and users

Customers own their profiles and membership data. Staff process loyalty operations. Managers additionally manage employees, reward definitions and account status. The implementation has seven entities and 27 routes. It uses NestJS, TypeORM, MySQL, JWT and bcrypt. Frontend development is optional in the final-project instructions; Postman is the client used in this package.

The scope is one store. POS/payment integration, points expiry, account recovery, production migrations and a graphical customer portal are future work. GitHub publication, the student's recording and live presentation remain personal deliverables.

## 2.2 Business rules

The student confirmed one point per PHP10 purchase. Each purchase rounds down independently: PHP1500 earns150 points; PHP19.99 earns1. PurchaseAmount uses DECIMAL(10,2) in pesos, as in Activity 4. Calculation first converts to integer centavos. Purchases below PHP10 do not create a zero-point ledger row because the lab's Points constraint requires a nonzero value.

Earn takes a purchase amount and calculates points on the server. Adjust takes a signed nonzero integer and cannot create a negative balance. Redeem can only be generated by the redemption workflow. Every balance change writes a ledger entry within the same database transaction.

A customer has exactly one membership account. Only Active accounts may start Earn, Adjust or Redeem operations. Managers can suspend/reactivate membership. Customers cannot directly edit balances or another member's records.

A redemption reserves one unit of an Available reward when enough points and stock exist. It begins as Pending. Staff/Managers can Complete or Cancel it. Cancellation appends a compensating Adjust entry and restores stock exactly once. The original negative Redeem entry remains. Completed and Cancelled are terminal; repeating the same final status is safe.

## 2.3 Nonfunctional requirements

Passwords are hashed and excluded from responses. Input validation and database constraints protect data integrity. JWT and roles protect routes; customer ownership protects individual records. Transactions and row locks preserve points/stock under concurrency. Lists use bounded pagination and sorting uses allowlisted fields. Email failure must not undo a successful loyalty operation. TLS is available for encrypted transport when configured.

# 3. System Architecture

## 3.1 Components and integration

The client sends JSON/HTTP requests to NestJS. Guards verify JWT, current role and resource ownership. DTO validation checks input. Resource controllers invoke services. Services use TypeORM repositories and transaction-scoped EntityManagers to read/write MySQL. Successful resources return as JSON; errors use a standard structured response.

[ARCHITECTURE_DIAGRAM]

The email path is separate: a business transaction writes an EmailNotification row as Pending. A dispatcher later reads pending rows, resolves the customer/employee email and sends through a configured SMTP transport. SMTP acceptance updates Sent and DateSent; rejection records Failed. A preview command writes local unsent text files without contacting SMTP.

## 3.2 Registration request flow

POST /api/v1/customers reaches CustomersController after CreateCustomerDto validation. CustomersService hashes the password and starts a database transaction. It saves the Customer, one LoyaltyAccount and one Pending welcome notification. On success, it returns the safe profile and accountId without a hash. If uniqueness or another constraint fails, all three writes roll back.

## 3.3 Redemption request flow

A Staff/Manager POST /redemptions reaches TransactionsService. It locks the LoyaltyAccount, checks Active status, locks Reward, verifies availability, stock and points, then reduces the balance/stock. It saves a negative Redeem ledger entry and a linked Pending Redemption. Customer and manager notifications enter the same transaction's queue. MySQL commits these changes together, or rolls them all back.

The lock order for redemption and status changes is account, reward, redemption. Cancellation holds those locks before checking the current state, preventing duplicate refunds. The mail dispatcher runs outside the loyalty transaction, preventing slow SMTP from holding points/stock locks.

# 4. Database Design

## 4.1 Entity relationship diagram

[ERD_DIAGRAM]

Customer has one LoyaltyAccount. Each account has many PointsTransactions. Each transaction references its processing Employee. A Redeem transaction may have one Redemption, and a Reward may appear in many redemptions. Customers and Managers may receive many EmailNotifications. Foreign keys restrict deleting referenced transaction history.

## 4.2 Entity dictionary

Physical table/column names follow Activity 4. The API uses camelCase properties, following Activity 5.

|Table|Primary key|Fields and relationships|
|---|---|---|
|Customer|CustomerID INT|FirstName/LastName VARCHAR(50), Email VARCHAR(100) UNIQUE, PasswordHash VARCHAR(255), PhoneNumber VARCHAR(15) NULL, BirthDate DATE NULL, DateRegistered DATE|
|Employee|EmployeeID INT|FirstName/LastName VARCHAR(50), Email VARCHAR(100) UNIQUE, PasswordHash VARCHAR(255), Role VARCHAR(10), DateHired DATE|
|LoyaltyAccount|AccountID INT|CustomerID UNIQUE FK, PointsBalance INT, AccountStatus VARCHAR(10), DateOpened DATE|
|PointsTransaction|TransactionID INT|AccountID FK, EmployeeID FK, TransactionType VARCHAR(10), Points INT, PurchaseAmount DECIMAL(10,2) NULL, TransactionDate DATETIME|
|Reward|RewardID INT|RewardName VARCHAR(100) UNIQUE, Description VARCHAR(255) NULL, PointsRequired INT, StockQuantity INT, ReorderLevel INT, RewardStatus VARCHAR(12)|
|Redemption|RedemptionID INT|TransactionID UNIQUE FK, RewardID FK, DateRedeemed DATETIME, RedemptionStatus VARCHAR(12)|
|EmailNotification|NotificationID INT|CustomerID NULL FK, EmployeeID NULL FK, NotificationType VARCHAR(15), Subject VARCHAR(100), Message TEXT, DateSent DATETIME NULL, DeliveryStatus VARCHAR(10)|

## 4.3 Constraints and normalization

Each table has an auto-increment primary key and atomic attributes. Contact/profile data is separate from membership balances and transaction history. The unique LoyaltyAccount.CustomerID enforces one account per customer. Redemption.TransactionID is unique. Unique customer/employee emails apply within each independent table; an optional accountType disambiguates login if the same email exists in both.

Database CHECK constraints enforce nonnegative balances/stock/reorder level, positive reward cost, allowed role/status values, nonzero signed ledger points, valid Earn/Redeem/Adjust field combinations and exactly one email recipient. DateSent must be present only for Sent notifications. These complement DTO validation rather than relying only on application checks.

PointsBalance is a cached value derived from the ledger and therefore intentional redundancy. All balance changes update both in one transaction. Tests reconcile PointsBalance with SUM(Points). The original Redeem debit snapshots reward cost, so later reward edits cannot change cancellation refunds.

## 4.4 Schema lifecycle and export

Setup initializes an empty development database from entities and explicitly adds CHECK constraints. Runtime synchronization is disabled. Version1 used different tables; setup refuses a detected v1 schema and directs the user to a new loyalty_v2 database. This package does not claim to migrate old data.

The included SQL export contains actual synthetic test records from MySQL, with all customer/employee login hashes disabled. ## 5.1 Requests and responses

Registration body: {firstName,lastName,email,password,phoneNumber?,birthDate?}. The response includes customerId, safe profile/date fields and accountId. Passwords/hashes are never returned.

Earn example:
```json
{"accountId":1,"transactionType":"Earn","purchaseAmount":1500}
```
Response201 includes transactionId, accountId, employeeId, transactionType Earn, points150, purchaseAmount1500 and transactionDate. An Adjust request uses a nonzero points integer and omits purchaseAmount. Redeem cannot be supplied directly.

Reward definition: {rewardName,description?,pointsRequired,stockQuantity,reorderLevel,rewardStatus}. PUT requires every editable field except optional description; omitting description resets it to NULL. PATCH uses any subset. RewardStatus is Available or Unavailable.

Redemption body:
```json
{"accountId":1,"rewardId":1}
```
Response201 includes redemptionId, transactionId, rewardId, dateRedeemed and redemptionStatus Pending. PATCH accepts Completed or Cancelled. Detail/history responses enforce ownership for customer tokens.

## 5.2 Lists, errors and status codes

Lists return {page,limit,totalItems,data}. Default page1/limit10, maximum limit100. Customer searches support name/email. Account lists filter by status. Ledger histories filter by transaction type. Rewards support search, status, lowStock, allowlisted sortBy and sortOrder. Notification lists filter by type/delivery status. A customer redemption list returns only their own records.

|Status|Meaning|Example|
|---|---|---|
|200|Successful login/read/update|GET own account|
|201|Created|POST customer, Earn or redemption|
|204|Deleted with empty body|DELETE unused customer|
|400|Invalid request|Invalid email, null field, bad query|
|401|Missing/invalid identity|No token, wrong password, expired JWT|
|403|Access denied|Other member's account or wrong role|
|404|Missing record|Unknown reward/account|
|409|Conflict|Duplicate email/name, insufficient points/stock, history restriction|
|429|Rate limit|Sixth failed login attempt within the window|
|500|Unexpected error|Sanitized server failure|

Errors contain success=false, statusCode, message, errors array and ISO timestamp. DELETE204 has no body. Complete endpoint contracts, examples and field constraints are in docs/API.md and the Postman collection.

# 6. Authentication and Security

## 6.1 Login and token lifecycle

AuthService looks up a Customer and/or Employee by lowercase email and compares the submitted password with a bcrypt hash. Login accepts optional accountType customer/employee. Ambiguous matching identities are rejected unless the caller specifies the type. Unknown email and wrong password use the same generic401 response.

Successful login returns a signed HS256 JWT valid for one hour. Payload fields include sub, type, role, email, iat and exp. The type distinguishes equal numeric IDs from the two account tables. No password or hash appears in the token. Clients send it through Authorization: Bearer.

## 6.2 RBAC and ownership

The global SecurityGuard verifies token signature/expiry, reloads the current database identity and checks allowed roles. Employee role values Staff/Manager map to staff/manager in authorization. Customer tokens use customer. Current database role controls permission even if an older token claim differs.

Customer access is checked against CustomerID directly or through LoyaltyAccount and PointsTransaction links. This applies to profile, account, ledger, redemption detail/list and email history. A valid token alone does not grant another customer's data. Staff/Managers process Earn/Adjust/redemptions. Manager is required for employee management, reward changes, account-status changes, deletes and the full delivery log.

## 6.3 Passwords, input and rate limiting

bcrypt cost12 protects stored passwords. New passwords are 12-72 ASCII characters, respecting bcrypt's input limit. Password columns use select:false and safe response construction removes hashes after account creation. DTOs validate email, names, dates, phone format, ranges, statuses and required fields. Unknown body fields and null values are rejected. TypeORM parameterized queries and allowlisted sort fields avoid constructing SQL from raw user input.

Five failed logins/minute are allowed for an IP/email pair. In-flight attempts reserve a slot so simultaneous requests cannot all bypass the limit. A general120 requests/minute/IP limit also applies. Both are local in-memory mechanisms; production needs distributed storage and proper trusted-proxy configuration.

## 6.4 TLS and remaining limits

NestJS accepts optional TLS_CERT_FILE and TLS_KEY_FILE and serves HTTPS when both are configured. A self-signed local certificate was tested. Default loopback HTTP is for setup and is not described as encrypted. A real deployment needs a trusted certificate/TLS termination. Certificate keys, .env and mail previews are excluded from Git and deliverables.

No refresh-token/password-reset/revocation UI is provided. Tokens normally expire in one hour. No idempotency key exists for new loyalty transactions. After a lost response, inspect history before retrying. Email dispatch is at-least-once under manual retry, not guaranteed exactly-once delivery.

Customer and Reward are separate modules with independent controller/service classes. Transaction-sensitive methods use the transaction EntityManager for all state writes. The runtime does not automatically change the schema.

## 7.2 Email queue and delivery

Account creation/profile/status changes queue AccountUpdate messages. Earn/Adjust/redemption changes queue PointsUpdate or RewardUpdate. Reward changes queue catalog updates to customers. Low-stock events queue RewardUpdate alerts to Managers through EmployeeID.

The preview command writes up to100 local text files and leaves status Pending. The dispatcher processes up to100 Pending notifications through configured SMTP. A MySQL advisory lock prevents simultaneous dispatch workers. Accepted messages receive Sent/DateSent; rejected messages receive Failed/NULL. Failed rows are retained for explicit review/retry. SMTP acceptance does not guarantee final inbox placement. No real external recipients were contacted during verification.
